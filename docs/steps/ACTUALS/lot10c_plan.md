## Existing contracts to reuse

Important current gap: `ProjectEditViewModel` and `ReservationEditViewModel` contain configuration only; neither includes an Actuals chronology. `ProjectRequirementEditViewModel` also omits RAF authority, so the ordinary Project editor currently offers an editable RAF field even where Domain rejects changes. 10C must expose this state clearly and preserve exact quantities through display and rebase.

## ViewModels and form adapters

1. Add a small Application read model, either `projectActualsViewModel.ts` / `reservationActualsViewModel.ts` or a shared builder with typed variants, exported from `src/application/index.ts`. Build from `PlanningSessionState`, never from timeline geometry or reconstructed daily values. Include object ID, `actualsFromDate?`, immutable ordered record rows, latest through date, current configured Team rows in Portfolio order, Team labels, and exact serialized cumulative/RAF strings. Keep historical rows even when their Teams are no longer configured; Team deletion guards ensure labels remain resolvable. Expose each current Project requirement's RAF authority/current exact RAF and its most recent historical cumulative **and** RAF, if any. For a reintroduced Team, the suggestion baseline is its current configured RAF, not an obsolete historical RAF. Add the minimal `rafAuthority` information to `ProjectRequirementEditViewModel` so the ordinary editor can explain/disable a latest-Actuals governed RAF while still serializing its exact value for unrelated configuration Apply.
2. Build form adapters under `src/ui/project-actuals/` and `src/ui/reservation-actuals/` (a shared parser/helper is fine). Parse CivilDates with `createCivilDate`; parse exact decimal or fraction input using `parseExactQuantityInput` and `consumedWorkloadFromSerialized` / `remainingWorkloadFromSerialized`. Preserve the untouched exact serialization as existing edit forms do: the three-decimal display from `formatQuantityForEditing` must never round an unchanged `1/3` into a new business value. Return typed existing append commands with current Team IDs. Local checks cover missing/malformed fields and helpful focus; the Domain remains authoritative for chronology, membership, nondecrease and RAF validity.
3. The read model should carry a reference fingerprint (latest record through date and current Team IDs; include exact latest cumuls/current RAF for detecting changed baselines). The form is built from **committed** state, never from an unsaved forecast/configuration draft. Label the sections “Forecast settings”, “Recorded Actuals”, and “New Actuals” so values cannot be confused.

## Draft model and card interaction

Create per-kind, per-object Actuals draft stores in the coordinator, separate from the existing Project/Reservation forecast draft stores. A draft contains open/closed editor state, through-date text, first-only from-date text, ordered Team input texts, untouched exact references, Project RAF suggestion provenance/dirty flag, errors, and a baseline fingerprint. Reading or expanding the history is view state, not an Actuals draft. The Portfolio card's expand/collapse state stays owned by the existing forecast draft store; collapsing a card hides both sections without discarding either draft. The shell's dirty indicator is the OR of forecast and Actuals dirty flags. Multiple cards and both kinds of drafts may stay open simultaneously.

The Actuals form is a **separate `<form>`**, not nested inside the existing forecast form made by `createProjectCardControls` / `createReservationCardControls`. Mount it as a sibling inside the same card host, with distinct Apply, Cancel, error region and accessible labels. Prevent form submission navigation. Its input/change handlers update only its Actuals draft store and card badge; they never call `input.dispatch`, `renderProjection`, or the forecast controller's `notifyDraftChange`. Keep history in a read-only list/table with dates, per-Team exact cumulative values, Project RAF values, and explicit period labels: first `[from, through]`, later `(previous through, through]`. Old records have no input, edit, or delete action. Show empty/zero-Team photos clearly. Forecast settings remain separately editable.

On starting a new photo, default `actualsThroughDate` to the next civil day after the last through date when possible, otherwise to a reasonable planning/cursor date that is valid for a first photo; this is editable and not a date rule. For a first photo, show a required blank `actualsFromDate` (or a clearly labelled, editable proposed date), never silently infer it from horizon, Project earliest start, or Reservation start. On later photos, omit the from-date control and omit the command property. A one-day first period is allowed; subsequent dates must be strictly later. A date may be outside the planning horizon and is independent of a future 10D knowledge snapshot date.

For each **currently configured** Team, prefill cumulative consumed from its latest historical entry anywhere in that object's chronology, or zero if none. Never copy the prior record's Team list as the new membership; an absent or reintroduced Team gets its latest historical cumulative. For Project, prefill RAF as an editable **suggestion**: `max(0, previousRemaining - (newCumulative - previousCumulative))` using exact Rational arithmetic. For an unchanged continuing Team, `previousRemaining` is its current RAF; for a reintroduced Team, use its current configured RAF. Initial delta is zero, so the initial suggestion equals current RAF. Recompute the suggestion when cumulative input changes only while the RAF field remains untouched; once the user edits RAF, never overwrite it automatically. Handle malformed/decreasing interim text without pretending a valid suggestion exists. No Domain RAF equation is added. Reservation shows only cumulative consumed and does not touch ratio/fixed-daily.

**Forecast/Actuals coexistence:** An Actuals draft always reads the latest committed business state. An unsaved Forecast draft never supplies membership or values to an Actuals command, and is never merged implicitly. Before Actuals Apply, compare that same object's Forecast draft against its committed reference: if Team membership changes, or a Project `current-configuration` RAF baseline changes, **block locally without dispatch**. Keep both drafts and say that the Forecast changes must be applied or cancelled first. Independent unsaved name, grouping, color, date, or Reservation forecast amount edits may coexist and survive the Actuals Apply. After a Forecast Apply actually changes membership or a Project RAF baseline, rebase the Actuals draft against committed state: keep typed values by TeamId for remaining Teams, remove absent Teams from the current form only (history stays intact), add new Teams as unresolved required rows, and recompute only untouched RAF suggestions. Block Apply until those rows are valid. Never overwrite manually entered RAF. When an Actuals Apply changes committed Project RAF and authority, rebase the Forecast draft: untouched RAF takes the new exact value; a local RAF edit now incompatible with `latest-actuals` stays visible with an explicit non-applicable error and is never dispatched as authorized. Extend the existing rebase/control state for this case; `choose(local, old, next)` alone is insufficient. Domain remains final authority. Cancel on either form clears **only that form's** draft and errors and leaves the other form/card drafts intact. On successful Actuals Apply, clear only that Actuals draft, keep its card expanded, and show the new history row.

On any successful command and remount, rebase all surviving Actuals drafts by ID alongside existing forecast drafts, preserving user text and open states. The existing backup import reloads the page, so no local draft survives that separate lifecycle. Do not reinitialize another card's form from the new read model merely because its controller is destroyed and recreated. On deletion, clear that object's drafts after success; historical objects already reject deletion. Guard Team deletion when its pending Actuals draft names that Team (similar to existing forecast draft checks), while the Domain retains its historical Team deletion rule. Existing UI snapshot restoration keeps viewport, cursor date, progress view, active tab, and card expansion; test these together with Actuals form state. Restore focus to the relevant New Actuals control or saved row after Apply/Cancel and errors.

## Apply and error handling

Project Apply constructs `{kind: "append-project-actuals", projectId, actualsFromDate? /* first only */, record: {actualsThroughDate, teams: [{teamId, cumulativeConsumed, remainingWorkload}]}}` from **all current Project requirements**. Reservation Apply constructs the corresponding `append-reservation-actuals` command from **all current Reservation allocations**, with no RAF or forecast amount. Do not mix an unsaved forecast membership into either command. If an object has zero current Teams, an empty `teams` array is the complete photo and is valid if Domain accepts it.

Call `input.dispatch(command)` once. A failed parse or Domain error leaves the local form and all session/projection/backup state unchanged; show `DomainError.path`/message next to the relevant date or Team field and a summary in the form's `role=alert` region. `ACTUALS_DATE_NOT_INCREASING`, first-date errors, `ACTUALS_CUMULATIVE_DECREASE`, `ACTUALS_MEMBERSHIP_MISMATCH`, and `COMMIT_FAILED` need understandable messages; unknown IDs and stale baselines must not be silently retried. On success, the existing dispatcher validates candidate state, rebuilds reconstruction/planning/timeline, writes V4, then publishes. Rebase other drafts before `renderProjection`, as existing Apply paths do. The new history row, timeline Actuals segment, diagnostics, and cursor metrics then reflect the committed photo immediately. A projection or storage failure must retain the form and prior UI projection.

## 10B presentation check

During implementation, inspect whether the Actuals tooltip should say “reconstructed daily consumption” rather than imply a user-observed daily value; this is a presentation wording change only. The card history supplies the **entered cumulative and RAF** values that a daily tooltip cannot show. A successful Apply on an out-of-horizon record may update history without a visible segment at the current horizon: show a clear saved state in the card and do not invent a timeline row outside the horizon.
