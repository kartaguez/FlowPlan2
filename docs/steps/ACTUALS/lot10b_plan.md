`src/domain/capacity/calculations.ts` computes effective capacity, active Reservation requests, `projectCapacity = max(0, effective - reserved)`, and `isOverReserved = reserved > effective`. Fixed daily request applies on working dates with a capacity period even when effective capacity is zero; ratio request follows effective capacity. Exceptions can supply effective capacity on non-working dates, while Reservation forecast still requires a working day. In `src/domain/planning/engine.ts`, `planTeam` independently calculates effective, reserved, available and over-reserved for every horizon date. `deadlineAccessibleCapacity` calls `projectCapacity` again for future dates not already cached, including dates past the horizon. This is a real second capacity path. Admission, deadline consumption and normal fair allocation all use the daily `available`; deadline lookahead uses the second path plus residual trajectories. The current `TeamDayCapacity` carries effective, reserved, project capacity and one `overReserved` flag. `TEAM_OVER_RESERVED` is emitted once per Team/day when forecast Reservations alone exceed capacity.

`buildTimelineViewModel` copies day capacity fields, derives named active Reservation requests independently, and builds Project forecast allocations only for active Projects. `buildTimelineGeometry` clips the reserved region at effective capacity and scales the tube from maximum effective capacity; `buildReservationSegments` scales names into that clipped region. Thus a zero-capacity day or over-capacity request has an exact model value but no full visible load. `calculateCursorMetrics` sums effective, requested reserved and Project allocations from horizon start through selected date; Occupied is reserved plus allocated, Occupancy is Occupied/effective, and daily over-reservation is `max(0, reserved-effective)`, summed before the ratio. Global metrics sum Team quantities before division. The Project progress numerator is forecast allocation and denominator is current RAF; Program/Pas progress combines active Project forecast allocation/RAF with active Reservation forecast request over the horizon. UI renders four capacity values and existing forecast progress.

The session dispatcher builds a candidate projection before V4 persistence/publication, so an Actuals append already follows the atomic projection path. The UI coordinator recomputes cursor metrics from the current `PlanningResult` on cursor movement without replanning. The Domain and all presentation paths use exact rational business quantities; Geometry alone converts to `number` for pixels.

## Input boundary and daily arithmetic

1. Extend `PlanningInput` with a required immutable `actualOccupation` value: an array of `{teamId, date, projectActual, reservationActual}` rows, each a non-negative exact `Capacity` (or a semantically equivalent exact non-negative Domain scalar). One row per Team/date with a nonzero source total; absence means two zeros. The engine validates unique Team/date keys and known Teams, accepts dates outside the horizon, and never reads records, record indices, source IDs, chronology, `actualsThroughDate`, or reconstruction weights. Keep the 10A `contributions` upstream for source-aware Timeline presentation. At the reconstruction/application boundary, derive the two row amounts by summing contributions by `sourceKind`; assert their sum equals `teamDayTotals` for every key, then freeze the rows. Do not change the 10A persisted V4 record format.
2. For Team/day let `C = effectiveCapacity`, `P = projectActual`, `Q = reservationActual`, `A = P+Q`, `R = active forecast Reservation request`, `F = Project forecast allocation`, and `B = max(0,C-A-R)`. All are exact non-negative rationals. `P`, `Q`, and `R` are never clamped; `0 <= F <= B`. `R` follows its current applicability and amount rules. Inactive entities still contribute `P` or `Q` from their records; only their forecast is excluded. Actuals before/after an entity's forecast dates or outside the horizon retain their own dates. There is no global cutoff. Within the horizon, applicable Actuals and Reservation forecast are both counted even when they belong to the same Reservation; this follows the decided independent actual/forecast axes and the specified capacity formula. The Project's existing RAF is the only forecast workload input and is never reduced again by reconstructed Actuals.
3. Add one Domain daily capacity calculation, taking `Team`, date, working pattern, active Reservations and the two calculated Actual amounts, returning immutable `{effectiveCapacity, projectActual, reservationActual, reservedCapacity, projectCapacity, actualOverCapacity, reservationOverCapacity}`. It calls the existing effective/Reservation request rules once per date and computes `B`. `actualOverCapacity = max(0,A-C)`; `reservationOverCapacity = max(0,A+R-C)-actualOverCapacity`. These two non-negative quantities partition `max(0,A+R-C)` and attribute excess in the prescribed order. No Project forecast can increase excess. Keep the old `projectCapacity`/`isOverReserved` API only if it delegates to this source of truth with zero Actuals; otherwise replace callers and retire it. `planTeam` caches the returned daily snapshot by CivilDate, and both the horizon loop and `deadlineAccessibleCapacity` obtain their base capacity from that same cache/factory, including lookahead dates beyond the horizon. Deadline residual trajectories and daily caps remain applied after this common base. Do not precompute unbounded future dates: retain the existing lazy lookahead cache and performance characteristic.
4. `TeamDayCapacity` adds `projectActualCapacity`, `reservationActualCapacity`, `actualOverCapacity`, and `reservationOverCapacity`; retain `effectiveCapacity`, `reservedCapacity` (explicitly **forecast** Reservation demand) and `projectCapacity` (now `B`). Replace the ambiguous sole `overReserved` flag with derived or explicit `reservationOverCapacity > 0`, plus a separate `actualOverCapacity > 0` signal. Ensure one immutable ordered row per horizon day, even at zero effective capacity. Project plans, admissions and allocations remain forecast only. Source-level Actuals contributions do not become Project allocations or Project plans.

## Diagnostics and projections

Keep `TEAM_OVER_RESERVED` as the Reservation **forecast incremental** excess diagnostic, emitted iff `reservationOverCapacity > 0`. This reproduces the old code and triggering behavior when Actuals are empty, and also reports Reservation forecast that pushes an Actual-loaded day over capacity. Add `TEAM_ACTUALS_OVER_CAPACITY` iff `actualOverCapacity > 0`. Both can occur on one Team/day; emit each once with the Team/date. Carry the two exact excess amounts in `TeamDayCapacity`, while diagnostics remain event codes. Update diagnostic text and red grouping; keep the existing deadline/unplanned codes and their attribution. A forecast Reservation that is positive while Actuals already exceed capacity produces both diagnostics. A forecast Reservation that fits within capacity after Actuals produces neither Reservation diagnostic nor excess.

Cursor capacity metrics use the inclusive horizon-start-to-selected-date interval. For each day, `Occupied = P+Q+R+F`; `Occupancy = ΣOccupied/ΣC` (undefined at zero denominator, otherwise unclamped). Expose separate cumulative `projectActual`, `reservationActual`, forecast `requestedReserved`, forecast `allocated`, `actualOverCapacity`, `reservationOverCapacity`, and `totalOverCapacity`. The displayed Over-reservation ratio becomes `ΣreservationOverCapacity/ΣC`; expose actual overload separately in the UI so the old four-value panel does not hide it. Undefined ratios at zero cumulative capacity remain undefined even when their numerators are positive. Sum daily excess *before* Team/global aggregation; unused days or Teams never compensate excess elsewhere. Global numerators and denominators are exact sums of Team values; never average ratios. `ΣtotalOverCapacity = ΣactualOverCapacity + ΣreservationOverCapacity`. On a run with zero Actuals all existing cursor capacity results and labels retain their values.

Keep Project, Program and Pas progress explicitly **forecast progress** in 10B: Project `allocated/current RAF`; Program/Pas aggregate active Project forecast allocation/RAF and active Reservation forecast request over the horizon, exactly as today. Actuals do not enter those progress numerators, denominators, or active-member filter; the UI continues to label them projected progress. This prevents double counting a historical Project consumption against a RAF already updated by Actuals. Actual-aware work/charge progress is a later product decision, not an accidental consequence of changing Occupied. Inactive historical Actuals still enter capacity and Occupied.

Timeline semantic contracts carry the distinct `P`, `Q`, `R`, `F` components and the two excess quantities on each Team/day. Project Actuals and Reservation Actuals are distinct semantic segments, including their 10A source ID where a named tooltip is useful; preserve source contributions upstream and clip to the visible horizon during adaptation. Forecast Reservation segments keep their names and exact full requests; Project forecast rectangles keep their allocation identity. Do not reuse forecast allocation styling or hit semantics for Actuals. Geometry should scale each Team lane against the maximum of effective capacity and total occupied on visible horizon days (with a safe zero case), draw a capacity reference and all four load categories in conceptual stack order, and reserve separate semantics for actual and Reservation forecast overflow. This removes the current `min(reserved,effective)` visual clipping and renders zero-capacity occupied days. Pixel heights may use `number`; exact quantities, diagnostics and tooltips come from Domain/ViewModel values. Update SVG classes/hits/tooltips and legend or labels so over-capacity Actuals and Reservation forecast are distinguishable. Preserve the single timeline axis, viewport, cursor and Project marker behavior.
