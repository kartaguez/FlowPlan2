The current `step_canon.md`, `current_canon.md` and parts of `canon.md` describe 10A cumulative records accurately for the current release. They must be revised **during implementation**, not in this plan-only pass. The old `recordIndex` is an array position and cannot be durable provenance after rectification or import. ## Proposed target contract

1. Add distinct `ProjectActualsSnapshot` and `ReservationActualsSnapshot` histories under their owning entities. Each snapshot has `{snapshotId, version, knowledgeDate, participation, coverage?}`; Project also has exact RAF per current Team. `coverage` is absent or `{actualsFrom, actualsThrough, periods}`. Every period has a stable `periodId`, inclusive `from/through`, and one exact nonnegative consumed value for **each** currently participating Team. Periods are ordered, contiguous, disjoint, and cover the global range exactly. Zero is stored explicitly. Reservation has no RAF. A snapshot contains no Forecast dates, Program, Pas, priority, capacity schedule, or planning result.
2. `participation` records current Team IDs in deterministic Portfolio order. A separate set of retired Team IDs with an explicit zero-current-Actual marker means that each retired Team has **zero current Actuals over the entire current object partition**; it is not a current participant. For a Project, this marker also means its current RAF is exactly 0, without adding it to the RAF map of participating Teams. The marker may be compact rather than materializing a zero in every period, provided validation and read models preserve that exact equivalence. When the partition changes while the Team stays retired, this zero follows the new partition automatically, without zero re-entry or invented consumption. Earlier snapshots remain immutable and retain their participating rows and RAF. Reintroduction ends this shortcut: explicitly validate the Team's values for every period in the then-current partition and, for a Project, its current RAF. Historical significance is derived from **any** snapshot with a nonzero consumed value or Project RAF for that Team, independent of current participation. Existing Team IDs remain stable.
3. A Project can have no snapshot, a snapshot without Actuals coverage and with explicitly zero RAF for every current Team, or a covered snapshot with explicitly zero consumed values. A snapshot without coverage may also carry positive RAF. These are distinct encoded states; absent RAF knowledge must never be represented or interpreted as RAF = 0. Within a Project snapshot, every current Team RAF is an exact nonnegative quantity, never `null` or `undefined`; no fourth nullable RAF state is introduced. A Reservation starts only with explicit Actual coverage, but later total erosion yields a snapshot without coverage. No Project/Reservation creation or Forecast-only edit creates a first snapshot. When a Project snapshot exists, its current RAF is mirrored into `ProjectTeamRequirement.remainingWorkload` for the unchanged planning interface; validate equality at the Portfolio boundary. Remove `rafAuthority` once V5 migration and consumers are switched: it cannot represent snapshot RAF without coverage or removed Team history.
4. Version is a positive, monotonically increasing integer **per object**, assigned from its persisted history; `snapshotId` is a stable kind/object-ID/version tuple, independent of array position. `knowledgeDate` comes from an injected application clock (`today(): CivilDate`), never a user input or hidden Domain clock. The Domain accepts explicit date/version/ID, checks uniqueness, consecutive version, nondecreasing knowledge dates, and `actualsThrough <= knowledgeDate`. Multiple writes on one day have distinct versions and total order. If a clock moves backward, reject with a visible error rather than backdate. A failed transaction or no-op consumes no version. The UI command must carry a base snapshot version for stale-draft detection.
5. Compare normalized business state, excluding snapshot metadata: coverage presence and bounds; ordered period boundaries and stable IDs **only insofar as IDs identify unchanged periods** (a replacement with the same boundaries and values is a no-op); exact canonical rational values by Team ID; participation and retired markers; Project RAF. Team/period array order is canonicalized, so reorder alone is a no-op. A changed partition is effective even if totals match. The first explicitly validated Project RAF-only snapshot is effective even if its RAF equals preexisting Forecast RAF; later identical submissions are no-ops. Snapshot creation is not a side effect of unrelated Forecast changes.
6. Mutations operate on one complete object candidate and carry an explicit operation intent/edited zone. Validate that untouched periods/Teams are copied verbatim and that every new or changed nonzero-area value is explicitly provided/confirmed. A split, merge, interior replacement, moved boundary or partial erosion never prorates or derives a nonzero consumed value. Only a zone whose old values for a Team are **all zero** may automatically become zeros for that Team. A newly participating Team must explicitly validate even all-zero entries. Do not enforce conservation of previous totals. There is no interior deletion leaving a gap: use a covered replacement with explicit zero when appropriate.
7. Extension may prepend or append one or several contiguous periods. Erosion may remove whole head/tail periods, trim an edge with explicitly validated new values, or remove all coverage. If `actualsThrough` changes, require explicit validation of **all** current Project Team RAFs, even if values stay the same; a past snapshot's RAF is never restored automatically. If only `actualsFrom` changes, current RAF may carry forward. Total erosion requires explicit RAF validation even though RAF becomes undated. RAF changes alone create a Project snapshot. RAF is nonnegative and arithmetically independent of consumed.
8. Add Team with existing coverage: one transaction adds the Forecast requirement/allocation and explicitly validated values for every current period, plus Project RAF. Other Teams carry forward. Remove Team only if every current consumed value is zero; Project RAF may be positive, but the removed Team's current state becomes explicitly RAF = 0 while earlier snapshots retain their old RAF. Show the final state and require explicit confirmation. On an object with a snapshot but no coverage, the same operation updates participation and Project RAF in one snapshot. Without any snapshot, existing Forecast membership behavior remains. Do not create a new snapshot for a pure Forecast change that has no knowledge impact.
9. Actuals are facts outside Forecast start/end/deadline and planning horizon; validation checks valid civil dates, coverage, nonnegative exact values and `actualsThrough <= knowledgeDate`, not Forecast bounds. `isActive` continues to affect only forecast participation. Projection may clip to its relevant horizon, but V5 stores complete knowledge. Capacity/calendar are reconstruction weights and never constrain accepted amounts.

## Ordered implementation sequence and acceptance gates

Each step is a separate reviewable dependency; the future implementation should keep the full suite green after migration reaches its relevant callers.

1. **Domain types and invariant factory.** Replace the business use of `src/domain/actuals/records.ts` with typed snapshot/coverage/period factories (retain legacy DTO types only for migration). Update `entities.ts`, `reservation.ts`, `domain/index.ts`, date/scalar helpers as needed. Validate optional coverage, exact common partition, unique IDs and Teams, nonnegative values, current participation, RAF and history order. Require no fixed day/month granularity. Tests: empty versus zero states, one-day and arbitrary periods, boundary adjacency, gaps/overlap, invalid dates, duplicate Team/period/snapshot IDs, multiple snapshots on one date, immutability. Risk: accidental collapse of absent and explicit zero.
2. **Pure whole-object transition service.** Replace `append.ts` and the cumulative checks with candidate construction for initial entry, RAF-only Project entry/change, extension, interior replacement/split/merge, edge erosion and total erosion. Supply injected knowledge identity and base-version precondition. Validate explicit-value evidence per changed zone; normalize and compare before assigning the next version. Test altered totals, exact no-op, partition change with same total, zero-only propagation, refusal to infer nonzero or prorate, future Actual refusal and same-day ordering. Risk: a generic form payload could bypass explicit confirmation; model confirmation in typed commands, not only UI flags.
3. **Membership and RAF integration.** Update `planningSession.ts`, `requirements.ts`, `entities.ts`, `capacity/reservation.ts` and Project/Reservation edit commands to commit Forecast membership plus any necessary object snapshot in one candidate. Replace RAF provenance and equality checks with snapshot-derived authority. A direct ordinary RAF edit on a snapshotted Project must route to explicit RAF knowledge action or fail. Retired zero Team markers and historical-significance queries drive removal/reintroduction and deletion guards. Preserve Team identity and previous snapshots on removal; set the removed Project Team's **current** RAF to the exact nonnegative value 0, even if its previous RAF was positive. Earlier snapshots retain their original RAF. Do not encode absence of RAF knowledge as zero or introduce nullable RAF. Tests: both object kinds, additions, zero/nonzero removals, RAF-positive removal, reintroduction, Forecast-only no-snapshot, stale base version, rollback. Risk: the present Forecast card builds all Team rows independently of Actuals; its Apply contract must change together with this service.
4. **Daily reconstruction and planning boundary.** Rewrite `reconstruction.ts` to iterate **only the current snapshot** and each exact period/Team amount. Extract/reuse `distribute` and its rational conservation/fallback checks. Keep `actualOccupationFromReconstruction`, `buildPlanningSessionProjection.ts`, `recomputePlanning.ts`, `planning/contracts.ts` and shared engine capacity formula; ensure zero rows retain knowledge in snapshots even if omitted from nonzero planning input. Clip derived rows only after full truth is available, including lazy deadline lookahead dates when needed. Tests: before/after horizon, outside Forecast bounds, capacity-weighted thirds, zero-capacity fallback, exact period and Team/day totals, inactive entities and no double count. Risk: a naive horizon clip before distribution changes totals and daily weights.
5. **Source identity, timeline and metrics.** Replace `recordIndex` in reconstruction contributions with `{sourceKind, sourceId, snapshotId, periodId, teamId, date}`; stable period IDs survive unchanged copied periods and new IDs identify replacement periods. Thread identity through `buildTimelineViewModel.ts`, `timelineViewModel.ts`, geometry, hit testing, SVG data, tooltip lookup and related tests. Tooltips identify reconstructed daily amount and source period/snapshot without claiming daily observation. `cursorMetrics.ts` and diagnostics remain sums of the current snapshot's derived occupation; forecast progress remains current RAF based. Verify current-only behavior, rectification replacing a source, exact overload split, no leaked historical totals or stale tooltip source. Risk: geometry presently drops provenance to object/Team/date, so the entire adapter chain needs attention.
6. **V5 persistence and safe legacy handling.** Extend `src/application/backup/flowplanBackupV1.ts` (or extract version modules), `planningBackupOperations.ts`, dispatcher, local backup and import/export tests. Define strict V5 schema with full snapshot histories, explicit absent coverage, canonical quantities, IDs/versions/date, participation, retired markers and Project RAF. Round-trip strict validation must reject forged gaps, future dates and dangling historical Team IDs. Keep V1–V3 reading as no-snapshot state. V4 has exact cumulative values and record boundaries, so per-record **legacy deltas** can be computed without rounding, but V4 has no knowledge dates or immutable snapshot IDs; it may omit Teams in records, and a reintroduced Team's delta can span absence while being assigned to one later interval. Do **not** pretend each V4 record was a dated target snapshot or fill missing Team periods with zero.

   Decode a V4 object with records into a lossless, read-only `legacyV4Actuals` **migration staging state**, not a second durable Actuals business model. V5 may retain that payload alongside later target snapshots as historical evidence, with explicit migration status; Forecast edits and backup rewrites must not discard it. No new Actuals/RAF knowledge may be written as V4 records, and no V4 append remains a target business command. Before reconciliation, only an explicitly legacy reconstruction adapter may project those records into the current simulation. The reconciliation UI may show exact interval deltas and current RAF as suggestions, but must obtain explicit current partition/Team values and RAF validation, require `through <= today`, then create the **first true snapshot at the current knowledge date**. After reconciliation, only the current V5 snapshot supplies simulation and business mutations; the V4 payload remains read-only/exportable and is never added, merged or implicitly arbitrated with that snapshot. For an object with legacy records, current projection has **exactly one source mode: legacy before reconciliation or snapshot after reconciliation**, never both; an object with neither legacy records nor snapshot has no Actuals source. Keep the cumulative reconstruction confined to the legacy adapter, outside the new snapshot Domain. For structurally unambiguous V4 cases, an optional assisted path may prefill every exact period delta, but still asks for explicit confirmation of all membership/coverage assumptions. A V4 with no Actuals and no explicit RAF knowledge becomes no-snapshot V5. Test V4 round-trip preservation, missing/intermittent Teams, nonzero reintroduction, future-through legacy, Forecast edits before reconciliation, rollback on write failure, lossless export/import, refusal of V4 append, and exclusive source selection before/after reconciliation.
7. **Current editor and history.** Replace `actualsViewModel.ts`, `actualsDraftStore.ts`, `parseActualsCommand.ts`, `createActualsCardController.ts` and coordinator wiring. Show the current common partition as rows and Teams as columns, exact consumed and current Project RAF. Provide initial arbitrary coverage, prepend/append, replacement/split/merge, edge/total erosion, RAF-only action, Team addition/removal/reintroduction and read-only snapshot history with knowledge date/version. The editor submits one typed whole-object command, with explicit confirmation markers for values and changed-through RAFs. Drafts retain a base snapshot ID, edited zone, exact text and untouched references; rebase only nonconflicting untouched fields, expose stale conflicts and never merge two partition edits silently. A Forecast membership draft and Actuals draft on the same object must be applied as one coherent action or explicitly sequenced with a rebase before the dependent Apply. Keep per-card independent Forecast/Actuals drafts, dirty indicators, viewport/cursor/tab state, Apply isolation and Cancel isolation. Test all workflows plus failed parse/projection/write, remount, independent cards, keyboard/focus and history read-only. Risk: 10C's single through-date form cannot express target partition operations and should not be stretched into an implicit cumulative command.
8. **Identity protection, documentation and closure.** Enforce physical deletion guards for Project/Reservation/Team when any significant snapshot **or retained V4 legacy record** requires its identity; zero-only non-significant history can be retained while policy is reviewed, but no referenced identity may disappear and break interpretation. Update `docs/steps/ACTUALS/step_canon.md` or add a successor target canon, `docs/current_canon.md`, `docs/canon.md`, `docs/current_plan.md`, and 10D/10E scope text so only the new snapshot model is described as current after validation. Run typecheck, build, complete automated suite, V1–V5 real-backup preflight/round-trip, transaction-failure tests and manual desktop/narrow UI review. Do not mark 10C.1 DONE until implementation is audited and validated.

## Test matrix that must survive implementation

Domain tests cover partition exact cover/contiguity/no overlap, negatives, the three distinct states (no snapshot; Project snapshot without Actuals coverage and with explicitly zero RAF; covered snapshot with explicitly zero consumed values), Project RAF-only first action, Reservation covered first action, extensions in both directions, interior repartition/split/merge with changed totals, zero-only automatic propagation including retired Teams across repartition, refused nonzero invention, whole/partial head and tail erosion, total erosion, RAF with/without coverage, changed-through explicit RAF revalidation (including erosion into the past), unchanged-through RAF carry, RAF-only edits, no-op, same-day version order, future Actual rejection, out-of-Forecast and out-of-horizon coverage, Project/Reservation Team addition, zero/nonzero removal, positive RAF removal ending at exact zero, reintroduction with explicit full partition and RAF, historical significance and identity deletion guards. Integration tests cover exact daily distribution/fallback/conservation, only current snapshot in planning, source IDs across rectification, timeline/tooltips/metrics/overload, V5 strict round-trip, each V1–V4 migration class, failed candidate/projection/write rollback, UI draft Apply/Cancel/rebase and read-only history. Keep existing 10B numerical capacity and forecast-progress tests as regression gates; rewrite tests that assert cumulative monotonicity or `recordIndex` as **legacy-only** tests, not target behavior.

## Boundary with 10D/10E

10C.1 versions **object-scoped Actuals/RAF knowledge only**. 10D must be re-scoped around any additional cross-object or Forecast knowledge required for historical whole-planning replay; a 10C.1 object snapshot alone does not freeze Team capacity schedules, working pattern, Forecast parameters or other objects at the same instant. 10E drift comparison must state which inputs are historical and which are current. Neither concern justifies writing a general Portfolio versioning system in 10C.1. No blocking functional question is identified for this plan; the V4 reconciliation gate is an intentional migration safety rule.
